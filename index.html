Spec-driven development

명세 주도 개발

A dedicated spec repo is the single source of truth. Every feature goes through specify → clarify → plan → tasks → implement, with a human approval gate between each stage — AI cannot advance the pipeline on its own.

  • Requirements clarified through 3 structured Q&A sessions (7 decisions recorded in the spec itself)
  • A 16-item spec-quality checklist gates entry into the planning stage
  • Tasks are triple-labeled (parallelizable? / repo / user story) so the FE/BE split is designed before coding starts

The team's ground rules live in a version-controlled "constitution" (6 principles, semantically versioned). When a meeting decision changes a rule — e.g. moving the API contract's source of truth from the spec repo to backend-generated Swagger after a real contract drift — the constitution is bumped and the change propagates to every downstream doc in the same commit trail.

별도의 명세 레포를 단일 진실 공급원(SSOT)으로 두고, 모든 기능이 specify → clarify → plan → tasks → implement 파이프라인을 거칩니다. 각 단계 사이에 사람 승인 게이트가 있어 AI가 임의로 다음 단계로 넘어갈 수 없습니다.

  • 구조화된 Q&A 세션 3회로 요구사항을 확정 (결정 7건을 명세에 직접 기록)
  • 16개 항목의 명세 품질 체크리스트를 통과해야 계획 단계 진입
  • 태스크를 3중 라벨링(병렬 가능 여부, 담당 레포, 유저스토리)해 코딩 전에 FE/BE 분담을 설계

팀 규칙을 유의적 버전으로 관리되는 '헌법' 문서(원칙 6개)로 명문화했습니다. 실제로 계약 드리프트를 겪은 뒤 회의에서 API 계약 정본을 명세 레포에서 백엔드가 생성하는 Swagger로 이관하기로 결정했고, 이 변경이 헌법 개정과 함께 하위 문서 전체에 같은 커밋 흐름으로 전파되도록 운영했습니다.

AI collaboration governance

AI 협업 거버넌스

  • 100% of frontend commits carry a Co-Authored-By trailer and a session URL — every change traces back to the AI session, the Jira ticket, and the decision behind it
  • 6 recurring workflows (release engineering, issue-quality rules, knowledge handoff) were encoded as natural-language "skills" the AI executes, instead of shell scripts
  • Long sessions hand off through a progress log and a resume protocol, so context loss across sessions doesn't silently drop work

Because a wrong risk judgment is a safety issue, the AI is only allowed to move a ticket to "In Review" — never to "Done." Final sign-off always requires a human reviewer and, for safety-critical logic, verification on a real device. This permission boundary is enforced at the tooling level, not just by convention.

  • 프론트엔드 커밋 100%에 Co-Authored-By와 세션 URL이 포함되어, AI 세션, Jira 티켓, 결정 근거까지 모든 변경을 역추적 가능
  • 반복되는 절차(릴리스, 이슈 품질 규격, 지식 이관) 6개를 셸 스크립트 대신 AI가 실행하는 자연어 '스킬'로 인코딩
  • 긴 세션은 진행 로그와 재개 프로토콜로 인수인계해, 세션이 바뀌어도 맥락이 조용히 유실되지 않도록 함

위험도 오판이 곧 안전 문제이기 때문에, AI는 이슈를 '검토 중'까지만 전환할 수 있고 '완료' 처리는 할 수 없습니다. 최종 승인은 항상 사람 리뷰어가, 안전 크리티컬 로직은 실기기 검증까지 거친 뒤에만 내립니다. 이 권한 경계는 관례가 아니라 도구 레벨에서 강제했습니다.

Why this matters

성과 & 의의

K-Bap isn't a showcase of "AI wrote the code" — it's a showcase of the process I designed around AI: the constitution, the approval gates, the permission boundaries, and the sign-off criteria. AI accelerates the work; the governance around it is what keeps a 2-person team's safety-critical product trustworthy.

  • Domain research across US/EU/Korean food-safety regulations to build an 81-item allergen & dietary model
  • Snapshot-locked regression tests on real menu OCR data to prevent silent safety regressions
  • A dual-tracking system (Jira as source of truth, a separate launch doc for the release big picture) to prevent status drift

K-Bap에서 제가 실제로 설계한 건 AI를 둘러싼 프로세스입니다. 헌법, 승인 게이트, 권한 경계, 완료 판정 기준 모두 그 설계의 일부입니다. AI는 작업 속도를 높이지만, 2인 팀의 안전 크리티컬 제품을 신뢰할 수 있게 만드는 건 그 주변의 거버넌스입니다.

  • 실제 메뉴판 OCR 데이터로 스냅샷 회귀 테스트를 잠가 안전 관련 회귀 방지
